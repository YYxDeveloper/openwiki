00 · 問題

AI 不是寫太少，是寫太多又驗不到

01

吞吐 ≠ 品質

LOC 暴增，但沒人敢 merge。速度不是目標，深度才是。

02

綠燈 ≠ 正確

build 過了、測試過了，真實行為仍可能是錯的。

03

沒有驗證迴路

每個結果都回到人手上手驗，agent 無法自己收斂。

if you want to go fast, go deep first. — poteto（Lauren Tan），React Compiler 維護者

只有三層，而且你只用第一層

階段 0 · 只做一次

Setup：先給 agent 一雙能自己驗證的眼睛

  • setup-pstack — 設定 role × model × reasoning budget
  • large / medium / small — 三個預算等級，決定 token 花費
  • verify-<app> skill — 讓 agent 像使用者一樣操作你的 app

最高 ROI 的一步

setup 問你要不要產生驗證技能時，說好。

能自我驗證的 agent 會一路跑到通過；不能的，每個結果都得你手驗。

/setup-pstack
  → 選 budget：large / medium / small
  → 逐角色確認模型（可設 inherit-parent / auto）
  → 產生 verify-<app>
  → 有併發 / 重試 / 狀態機 / parser → 再加 formal verification

階段 2 · Understand

改 code 之前，先確認你懂的是對的

  • pstack-how — 現在怎麼運作、新 code 該放哪
  • pstack-why — 為什麼長這樣、數字哪來
  • pstack-teach — 白話講懂一個子系統
  • pstack-recall — 跨對話撈回你最近做過什麼

兩個前置動作

in-your-own-words：讓 agent 重述你的目標與問題，錯在這裡改，只花一句話。

sharpen：把 prompt 改得更深（不是更大），回傳給你，不執行。

先讓它用自己的話重述問題，再讓它動手。 重述錯了，成本是一則訊息；動手錯了，成本是一個 PR。

階段 3 · Design

別讓第一版 code 鎖死形狀

情況用什麼它做什麼
跨函式邊界pstack-architect先定型別與模組形狀，再填實作
有便宜的實驗可定prototype做 2–3 個能跑的草稿，用看的選
同一份 brief 多候選pstack-arena並行產出，融合最強的部分
可切片的 fan-outpstack-swarm一 worker 一片，回一份報告
設計有爭議pstack-interrogate多模型審，主動想辦法弄壞它
怕弄壞 diff 之外pstack-blast-radius找出外部破壞面，並證明那條安全前提

判準：能靠跑一次解決的分歧，就不要用問的。

階段 3 · Design 補充

blast-radius：這個 diff 會弄壞什麼

輸入一個你不放心的小 diff／模組
找 diff 之外呼叫點、消費者、共用狀態
證一條安全前提用真實執行，不是寫報告
輸出影響清單 + 可重跑的驗證指令

跟 interrogate 差在哪

interrogate：審 diff 本身，找實作漏洞與回歸。

blast-radius：找 diff 之外，找連鎖破壞面。

判準：只列「可能受影響」卻沒有證明 → 不算完成。

pstack-blast-radius 這 12 行改動在 repo 內可能弄壞什麼？先不要改。
給我能重跑的驗證指令，並指出哪個共用假設被它依賴。

階段 3 · Design 補充

blast-radius 的合格產出

# 影響面
api/serializers.py:41  user_name → username
web/api/user.ts:12 · mobile/user.dart:88 · etl/sync.py:57

# 安全前提
「所有 consumer 都經同一支 mapper」
→ grep 證實無直接字串取值

# 證明
$ pytest tests/api/test_user_contract.py -q  → 14 passed
$ curl /api/users/1 | jq .username           → "alice"
可重跑：make verify-user-contract

合格

① 影響清單有 檔案:行號

② 至少一條前提被真實執行證明

③ 留下可重跑的指令

不合格

「可能影響付款流程，建議測試一下。」

沒有清單、沒有證明、不能重跑 —— 等於沒做。

它只保證它證明的那一條；其他面用測試或 swarm 補。

階段 4 · Build

Build：小步、可驗、先減後加

Feature

先講清楚 data shape，再往上長行為。

Bug fix

repro → 根因 → 修 → 用執行時證據收尾。

Refactoring

行為不變，只動結構；每一步都要能驗。

  • pstack-tdd — 只在那條測試便宜又真實時用；硬套 mock 證明力更低
  • no-comments — 審查前拔掉註解，讓審的人不是寫的人
  • unslop — 清掉文字裡的 AI 味，回覆也算
  • 原則 — Subtract Before You Add、Fix Root Causes

階段 5 · Verify

什麼才算「證明」

  • prove it works — 驗真的產物，不是 proxy、不是「它編譯過了」
  • verify-<app> — 腳本化驅動 app，跑完整流程並錄影
  • benchmark-checklist — 七個問題檢驗你量到的數字
  • formal verification — 測資碰不到的性質（併發、不變式）
✕ build 綠燈proxy
✕ 它說完成了自我回報
✓ 真指令輸出artifact
✓ 流程錄影 / 寫入值artifact

回覆只說「測試通過」時，追一句：跑給我看，貼真實輸出。

進階

用原則名轉向，比寫一段話更準

24 條不用背。對話中講出名字，agent 已讀過完整規則，一句話就能改方向。

用 subtract before you add。先刪過時 adapter，再設計剩下的。

apply prove it works。跑真的 import 流程，把寫入的紀錄給我看。

separate before serializing shared state。每個嘗試一個 worktree，不要鎖。

判準

回覆必須說明「哪個決定被這條原則改掉」。只報名字、沒講決定 = 沒真的套用。

先講清楚

這些不是 pstack 官方語法，它沒有內建縮寫。G／D／E 只用在你的筆記與口頭。

送進 prompt 時仍寫完整詞（或直接貼範例），因為 agent 讀的是語意，不是代碼。Pr ≠ PR（pull request）。

成本 · 1／3

貴的不是推理，是這三個乘數

×N

平行度

panel 一個 entry = 一個 subagent；swarm 切片數就是倍數。

×L

驗證層數

budget 一次搬動所有 role：medium 降一級、small 降兩級。

×R

重跑次數

done 沒寫清楚，同一 brief 就反覆來回。

級別Playbook為什麼
便宜Investigation · how · why · teach · unslop純讀，subagent 少
中Feature · Bug fix · Refactoring · tdd單線，一輪可收斂
貴arena · interrogate · swarm · hillclimb多模型／多 worker／多輪量測
最貴autonomous run · autopilot-full／stack長時間 + 每個 PR 重新驗證

成本 · 2／3

三個 profile，照抄就好

省錢 · side project

budget small

code 次強 / inherit-parent

panel 1（或不用）

只在 bug 與設計才叫 mode

平衡 · 常用建議

budget medium

code 最強 high

panel 2，跨廠商

日常任務都走 mode

攻堅 · 錯了很貴

budget large

code 最強 xhigh

panel 3 + formal verification

設計／併發／資料／對外 API 才開

  • 看 subagent 數 — panel 長度、swarm 切片，是最直接的成本係數
  • 降一級重跑同一任務 — small 也能過同一組 done，就不需要 large
  • 先修 done，再升模型 — 反覆失敗通常是判準寫不清，不是模型不夠強

成本 · 3／3

六個最常見的浪費

反模式省法
用 large 改文案直接叫模型改，不進 poteto-mode
4 個 panel 審 10 行 diff縮到 1–2，或改用 blast-radius
done 沒寫，來回五次花 30 秒寫可 pass／fail 的檢查
整包 repo 貼進 context給路徑，讓 how 自己找
autopilot 跑整夜但沒檢查沒有 done 的長跑＝燒錢繞圈
平行 agent 共用工作區各自 worktree，或 cloud subagent
成本 ≈ 平行度 × 驗證層數 × 重跑次數 調整順序：降平行度 → 降層數 → 降重跑。模型換便宜，是最後一步。
