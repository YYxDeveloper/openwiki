📌 影片摘要

AI 寫 code 最不缺速度，缺的是「寫對」與「證明寫對」。Cursor 官方外掛倉庫裡的 pstack（作者 Lauren Tan，@poteto）用 58 個技能、23 個劇本、24 條工程原則，把資深工程師腦中的流程變成 agent 可重複執行的機械：先復現、先讀懂、先定架構，最後用真實產物驗證。

核心主張只有一句：想要快，先要深（if you want to go fast, go deep first）。目標不是多寫程式，而是少寫、寫對、拿得出證據；驗證技能的投資報酬率最高，「能編譯」不算證據。

💡 核心重點與案例列表

1. 定位與規模：不是 prompt 大全，是「AI 工作手冊」

  • 作者背景：Lauren Tan（poteto），待過 Meta、Netflix、Cursor，React 核心團隊成員、參與維護 React Compiler。她說法很直白：不要像「20 個水貨工人組成的團隊」那樣交付。
  • 倉庫落點：cursor/plugins 下的 pstack/，MIT 授權，內容 169 份 Markdown 為主體，真正的程式碼集中在少數技能（如畫狀態圖的 statechart 帶整套 TypeScript 腳本與測試）。
  • 三個數字：58 個技能（34 個工作流技能 + 24 條工程原則）、poteto-mode 內建 23 個劇本、2 個專用子代理（poteto-agent、comment-sicko）。另有預設關閉的 benny 自動化包與一份十頁上手指南。
  • 核心洞察：這些不是程式碼，而是寫給 AI 看的流程規範；每個技能就是一個資料夾 + SKILL.md，說明「什麼時候用、怎麼一步步做」。

2. 安裝與 poteto-mode：總入口 + 可稽核的代辦清單

  • 安裝：Cursor 直接 /add-plugin pstack；Claude Code 先 /plugin marketplace add cursor/plugins 再 /plugin install pstack@cursor-plugins，指令會多 /pstack: 前綴。
  • 設定：/setup-pstack 偵測可用模型 → 選推理預算 → 分配角色。預設分工是「寫 code 給 Grok、最難的改動與文字判斷給 Opus 5.5」，凸顯多模型協作是設計前提，不是事後補丁。
  • 入口：/poteto-mode 收到目標後會①用自己的話複述目標 ②匹配一個劇本 ③把劇本步驟原樣抄進待辦清單 ④逐步呼叫其他技能。
  • 最喜歡的細節：決定跳過某一步時，該步驟不會消失，而是留在清單並註明跳過原因——省掉了什麼，一眼可見。這就是可稽核性（auditability）。
  • 23 個劇本覆蓋：investigation、bug fix、perf、hillclimb、runtime forensics（活進程 / 已抓 profile 兩種取證）、feature、refactor、prototype、視覺像素對齊、開 PR、看護 PR、合併上線，以及長時自主：autopilot、autopilot stack、orchestrate、安全暫停、接手進度；全都不匹配則交 figure-it-out 現場設計劇本。

3. 修 Bug 劇本：先復現，才有資格談修好

「那些可能有點用的雙保險，只是假設（hypotheses），不是修復（fix）——不能發布。」

  1. 自己先復現：不准一上來就請使用者幫忙復現。
  2. 二分法 + 假設排除：列出假設，逐一用執行時證據排除，禁止猜。
  3. 規劃修復：把實作交給子代理。
  4. 同一處驗證：原本的復現現在通過，才算數。
  5. 提交順序：讓「失敗的復現測試」排在修復 commit 之前。
  6. 開 PR：帶證據。

深入解析：第 1、4 步把「可驗證性」鎖在因果鏈兩端（before / after 同一腳本）；第 5 步讓 git history 本身成為證據鏈，reviewer 不必相信任何口頭描述。

4. 提示詞怎麼寫：五樣、兩不寫、一句話原則

要素內容範例
目標要達成什麼修掉這個 PR 的隱蔽 bug
完成標準什麼狀態算做完頁面閒置時不再每 750ms 飄移
想要的證據要看到什麼才算數先復現、再修復、並驗證
已知線索你手上的觀察閒置時 CPU 有固定週期抖動
真正約束不可違反的邊界先復現、先別改 code
  • 兩樣別寫：① 具體怎麼做（留空間給 AI）② 你對原因的猜測（你越講，它越往那個方向找，形成確認偏誤）。
  • 只記一件事：給它一個目標，再給它一個能檢驗的辦法。
  • 短提示合法：上下文已在對話裡時，「Do it」「Continue」就夠；換話題要說 New Task 讓它重新匹配劇本；想讓模式常駐，在選單按 Option+Enter 變成 custom mode。
  • 周邊小工具：poteto-help（只給一條可直接發的提示詞，不自己開工）、sharpen（把提示詞改深、不是改長）、in-your-own-words（先複述目標，錯了只花一條訊息）、blast-radius（一個小改動還可能弄壞什麼）、bro（把太技術的回覆翻成大白話）。

5. 動手之前先看懂：how / why / teach / recall

  • how：講清楚一個子系統「現在」怎麼運轉，像資深工程師帶你入職。
  • why：git 考古學——從 commit 記錄出發，並行查 issue、文件、聊天記錄，回答「當初為什麼這樣設計」；查不到也會如實說查不到。
  • teach：把 how + why 合成一張張圖講明白。
  • recall：從你過去的對話記錄裡，把某個主題的上下文重新撿回來。
  • 關鍵判斷：不先看懂就動手的 AI，往往只在「第一個看起來合理的地方」修掉表面症狀。

6. 設計階段：別接受第一版設計

  • architect：寫 code 之前先定呼叫方式、型別、模組邊界。
  • arena：多個子代理在各自 worktree 同時解同一題，由另一個模型家族的評審打分，選一個當底，再把其他方案優點嫁接過來。
  • swarm：把工作切成很多片，每片一個工人，最後合成一份報告。
  • interrogate：不同模型來攻擊你的 diff；只有「重跑命令能真的復現」的問題才留下。原則：用原型代替爭論。

7. 寫完 code 之後：TDD、unslop、no-comments

  • tdd：先寫一個會失敗的測試，再寫修復。
  • unslop：清掉 AI 味——不用破折號、不硬湊三點、不寫「希望這對你有幫助」。
  • no-comments：叫一個獨立子代理 comment-sicko 審註解，因為寫註解的人總會替自己的註解辯護。能留下的很少：license 標頭、公開介面文件。若註解說「千萬別刪」，它會建議把這個約束變成型別、測試或 lint 規則。

8. 驗證指南（全倉庫最核心）：能編譯不是證據

  • 說「完成」之前要檢查真實產物：CLI 改動就真的跑命令；介面改動就真的在 app 裡走一遍流程。
  • 專案若沒有讓 AI 操作 app 的辦法 → 生成「專案專屬驗證技能」；併發、狀態機這類難測的地方 → 生成形式化驗證技能，預設 TLA+。
  • 測出來的數字要過七個問題：是什麼限制了這個數字？快取是不是熱的？…
  • 指南的結論：在所有技能裡，驗證技能的報酬最高。

9. 交付與看護 PR：五個窄 PR 勝過一個大 PR

  • 開 PR 劇本把改動整理成有順序的小 commit，把證據寫進 PR 描述。
  • 看護 PR：盯著同一個 PR，依序處理衝突 → 評審意見 → CI。對評審意見保持懷疑：真問題就修，噪音就帶著理由回推（push back）。
  • 它只負責到「可以合併」為止，絕不自己按合併；真正合併交給上線劇本。
  • 每個 PR 合併前由一個全新代理獨立驗證——寫 code 的和判斷 code 的，永遠不是同一個。

10. 過夜合約與多任務編排：你去睡覺，AI 接著幹

過夜合約四要素

  • 目標：例如「遷移所有呼叫方」。
  • 完成條件：舊呼叫點為零、測試全過、舊介面刪除。
  • 權限：它能動哪些東西。
  • 逃生出口：卡住幾小時就停下來、寫明原因。

夜裡循環：檢查完成條件 → 做最小改動 → 驗證 → 有進展就 commit、沒進展就丟棄 → 在決策日誌記一行。早上你審的是「決策」，不是重讀一整夜的記錄。

最大的坑：時長不是完成條件。「跑八小時」永遠可以達成，卻不代表事情做完。

  • autopilot：每個 PR 一個負責代理，從寫到合併，但合併前必須由一群全新驗證者檢查通過。
  • autopilot stack：同上，但不合併，留給你早上親自過目。
  • orchestrate：跨好幾天的大專案；協調者只分配與檢查，自己不寫 code。並行時強烈建議每個代理獨立環境（雲端子代理或各自 worktree），否則會互相覆蓋檔案。
  • 隔天回來看：show me your work 看決策記錄，或 catchup 快速了解進展與待你決定的項目。

11. 24 條工程原則：不是拿來呼叫，是拿來當口令

  • Lazy protocol：偏向刪除與最小改動；先減後加，先清掉沒用的東西再往上蓋。
  • Prove it：對著真實產物驗證。
  • 修根本原因，不是症狀。
  • 把教訓寫進結構裡：同一句叮囑說到第二遍，就把它變成 lint 規則或腳本。
  • 使用方式：AI 跑偏時，說一句原則的名字，比寫一大段解釋更準。

12. 個人化與代價：ultateme / reflect / correct

  • ultateme：翻你最近的聊天記錄，總結你自己的習慣，生成一個以你名字命名的模式（作者也承認 poteto-mode 是個人風格，不必全盤接受）。
  • reflect：一次大任務後，把學到的東西沉澱成技能修改。
  • correct：更徹底——如果你總在糾正同一種錯誤，它會去改倉庫本身，優先序為 架構 → 型別與檢查 → 測試 → 文件。
  • benny 自動化包（預設關閉）：整理 Slack 的問題回報、復現並嘗試修復。

13. 14 個常見坑（節選）

  • 在提示詞裡逐一點名技能，反而打亂劇本本來的順序。
  • 完成條件寫得含糊（「讓它變得更好」）→ 循環沒有東西可以檢查。
  • 還沒信任這個循環就讓它自己跑 → 只是更快產出「沒檢查過的東西」。
  • 看到 build 通過就回報成功。
  • 平行代理沒隔離環境 → 互相覆蓋檔案。

14. 使用成本與限制（作者自己講清的）

項目說明
Token 成本子代理與評審小組都是額外開銷；指南稱這是「嚴謹的價格」。小改動不值得整套 poteto-mode。
平台綁定為 Cursor 設計；Claude Code 能裝，但 Bugbot、automations 等 Cursor 獨有步驟會被跳過並註記。
技能缺漏部分技能（如 deslop）不在本包，要另裝 cursor-team-kit。
沒有規劃技能作者觀點：最好的規格說明就是 code；要計劃，也等設計定下來之後再寫。

🚀 結論、操作指南與未來展望

本質總結

pstack 不是「讓 AI 寫更多」的工具，而是一套讓 AI 少寫、寫對、拿出證據的工作手冊。58 個技能、23 個劇本、24 條原則，背後是同一個想法：想要快，先要深。

具體操作：五步起步法（不用一次全裝）

  1. 先不要裝整套。第一天只正常寫提示詞，觀察 AI 在哪裡出錯。
  2. 同一個錯誤出現第二次，才加一個技能或一條檢查規則。
  3. 裝好後跑 /setup-pstack，選推理預算與模型分工，然後新開對話讓規則生效。
  4. 嚴謹任務一律 /poteto-mode + 目標 + 可通過/失敗的檢查；模式要常駐就 Option+Enter。
  5. 先投資驗證技能：讓 AI 能操作你的 app（CLI 或瀏覽器），報酬率最高。
# 提示詞模板（最多五句，每句一件事）
目標：<要達成什麼>
完成標準：<什麼狀態算做完，可通過/失敗>
證據：<要看到什麼才算數>
線索：<你已經觀察到的事實>
約束：<先復現 / 先別改 code / 不要動 X>

適用 / 不適用

適合不適合
有驗證辦法的非平凡任務、需要多代理平行的遷移、要過夜的批次工作、PR 品質要求高的團隊 一行小改、純探索性問答、沒有可檢驗完成條件的模糊需求

未來趨勢與可能進展

  • 「可驗證性」成為 agent 工具的核心貨幣：從「寫得快」轉向「能證明做對」，驗證技能會像 CI 一樣變成專案標配。
  • 多模型分工常態化：同一任務內不同角色用不同模型（寫 vs 審、快 vs 深），單一模型調參不再是唯一解。
  • Harness 無關化：pstack 已是 Cursor 外掛、Claude Code 可用；社群已有 pstack-claude 等移植版，Cusor 獨有步驟會被跳過，跨 harness 適配層會持續演化。
  • 個人化工作手冊：ultateme、reflect、correct 預示「agent 依你的習慣自我校準」的方向——從通用 prompt 庫走向個人工程風格編譯器。
