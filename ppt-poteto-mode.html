01 · 它是什麼

一句話：poteto 的做事風格，寫成規則

原文描述：簡潔詳細的回覆、有意識地使用 subagent、去 AI 味的文字、簡單的程式碼，以及驗證過的成果。

怎麼啟動只能手動輸入 /poteto-mode（設定了 disable-model-invocation）
它讀什麼你的任務 → 配對 playbook → 按步驟叫 skill
它怎麼收尾附證據的回報，而不是「我做完了」

03 · 非談判條件 1／2

開場與派工的三條硬規定

  • 第一則訊息 → 先講出你的目標，和最小可達成的改動，再開始做。
  • 啟動任何 agent → 第一行必須是「Read <path>/worker.md before anything else.」，因為營運規則只會從斜線指令載入，別的 agent 拿不到。
  • 能靠執行解決的分歧 → 直接做 prototype，不要來問你。
  • 每個回覆 → 點名「哪條原則改變了哪個決定」，且只能引用自己真的讀過的原則。

06 · 原則精選 1／2

什麼時候想起哪一條

原則白話
Laziness Protocol能刪就刪，改動越小越好，別亂加抽象層。
Foundational Thinking先想核心型別與資料結構，再寫邏輯。
Attack the Premise兩個修法失敗在同一個前提，先把前提寫下來並直接測它。
Subtract Before You Add先清掉死重，再往上蓋。
Build the Lever用工具（codemod、腳本）做，不用手改；工具本身就是可重跑的證據。
Exhaust the Design Space沒先例的設計，做 2–3 個原型比較再決定。

07 · 原則精選 2／2

驗證與委派的原則

原則白話
Prove It Works拿真實產物驗，不是「它編譯過了」。
Fix Root Causes追到系統第一次出錯的地方再修，不只加防護。
Test Behavior, Not Implementation測使用者看得到的行為，內部換了測試也不該壞。
Explain the Number量到的數字，先找出限制它的東西，並排除量錯了別的。
Guard the Context Window大量輸出交給 subagent，主對話只留摘要。
Never Block on the Human可逆的工作別問「要不要做」，做完給你看再調整。

08 · 自主程度

能直接做的，和一定要停的

直接做

可逆的事

用任何 MCP 工具；對外的可逆動作（團隊聊天、更新 ticket、啟動 eval）不用問。

一定要停

不可逆的事

對共用分支 force-push、部署、刪資料、發訊息給客戶。

  • 覆寫條件 — 你說「don't stop」「going to bed」「run until done」，就一路跑下去
  • 「不」是合法答案 — 被問要不要做、邀你加範圍，要給真實判斷；這件事不值得做就直說

09 · 派工

每次派 subagent 都要帶這四樣

1

背景執行

run_in_background: true

2

agent 模式

唯讀模式會拿掉 MCP，所以不用。

3

給路徑

用檔案路徑指過去，不要貼上整段內容。

4

指定模型

每個角色都要明確指定。

  • 劇本步驟內直接派的 subagent，用 subagent_type: "poteto-agent"
  • interrogate、swarm 這類流程技能自己會設定 type，照它的來
  • 你要為每個 subagent 的成果負責 — 看 diff，自己寫摘要

10 · 模型分級

三種工作，三種預設模型

工作預設模型
程式、文字、判斷claude-opus-5-5-xhigh-fast
瑣碎的機械式修改claude-opus-5-5-high-fast
多元評審／設計小組fable-5-2-high、opus-5-5-high-fast、gemini-4-neon-xhigh 各一
  • /setup-pstack 寫出的 pstack-models.mdc 會覆寫這些預設
  • Fable 5.2 是例外 — 只有你點名，或同一份 brief 兩次 Opus xhigh 都沒過檢查才用，「難」本身不算理由
  • 任何角色都不會超過 xhigh；Opus 5.5 一律用 -fast

11 · 配模型

依工作難度，上下調一兩階

↑ +1最難、最細膩
›
起點角色預設
›
↓ −1判斷類
›
↓ −2+例行工作
  • 起點是該角色的設定行或預設，維持同一家族，再調等級
  • 評審小組的座位維持原本等級，不調
  • 驗證永遠用 swarm workers 的模型
  • 模型代號被工具拒絕，就不要再傳。依序退回：角色設定 → 呼叫端技能的備案 → 同家族最近的代號 → 不指定 model，並說明

12 · 預設換新人

修正、追問、重試，都交給「新的」subagent

給新人什麼原本的 brief
之後所有的指示
前一位的報告與 branch

什麼時候才續用舊的

只有狀態「存在它裡面、搬起來很貴」的時候：

· 它的 checkout

· 它未提交的修改

· 它還在跑的程序

原因：舊對話會帶著舊的假設；新人從完整 brief 出發，比較不會延續錯誤。

13 · 回覆寫法

短句、先講你關心的、每句有證據

  • 短的陳述句 — 不用長破折號，不用冒號當連接詞
  • 先講「對你有什麼改變」
  • 每個主張附證據或標籤 — measured（量到的）、inferred（推論）、guess（猜的）
  • 你能自己跑的檢查，不要丟給人
我量到 p95 從 820ms 降到 390ms（measured）。原因我推論是少了一次 N+1 查詢（inferred）。 範例：標籤讓讀的人知道哪些是事實、哪些是推測。

16 · 常見誤會

五個最容易搞錯的地方

誤會實際上
「它會自動啟動」不會，只能你手動輸入 /poteto-mode。
「引用原則就好」要讀過那條的 SKILL.md，且說明它改了哪個決定。
「Fable 比較強就多用」只有點名或兩次 Opus 失敗才用。
「同一個 subagent 一直追問」預設每輪換新人，附原 brief 與前報告。
「PR 狀態用內建 babysit」要用 pstack 的 Babysit playbook。

18 · 解答

對一下答案

  • Q1 → Read <path>/worker.md before anything else.，<path> 是 poteto-mode 資料夾的絕對路徑。
  • Q2 → 不用。可逆工作直接做，完成後給結果讓人調整（Never Block on the Human）。
  • Q3 → claude-opus-5-5-high-fast。
  • Q4 → 預設換新的，附原 brief、之後的指示與前一位的報告和 branch。除非狀態只存在舊的裡面且搬很貴。
